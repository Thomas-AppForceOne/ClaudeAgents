# R7 — Runtime invocation bridge

## Problem

The orchestrator and agents are **markdown executed by Claude**, not a program. They can call only what is exposed as an MCP tool or a `gan` CLI subcommand. Today exactly one surface is exposed that way: the Configuration API (R1's MCP server). Every other framework library is reachable only by `import` — which a markdown orchestrator cannot do.

The consequence is that the run-store resolution layer plus four shipped, fully-tested libraries are **uncallable from the only orchestrator that exists**:

- **`src/config-server/storage/run-store.ts` (F7) — the keystone gap.** Every run-scoped tool below addresses its data by `runDir`/`repoKey`, and the orchestrator must export `GAN_RUN_DIR`/`GAN_WORKTREE`. Those identifiers come only from `resolveRunStore` / `generateRunId` / `computeRepoKey` / `resolveWorkspace` — import-only functions (re-exported from `src/index.ts`, but a markdown orchestrator cannot import). With no tool that *produces* a run context, none of the consuming tools below can even be called: the gap is upstream of all the others.
- **`src/trace/` (T1)** — the orchestrator is told to "emit a typed event at each milestone, agent attempt, LLM call, and tool call" and to drive the stderr heartbeat/summary formatters. It has no tool to do so. Real runs under the central store contain **zero** trace events.
- **`src/safety/` (A1)** — the per-role ceiling, sprint budget, and edit-oscillation checks are pure functions the orchestrator is told to call at every attempt boundary. There is no tool. No loop-detection halt can fire, because the check is never invoked and the `agentAttempt` events it reconstructs from do not exist.
- **`src/agents/evaluator-core/` (E3)** — the evaluator agent is told to "consume the evaluator plan" and "delegate every deterministic decision to evaluator-core." There is no tool that returns the plan; the agent reasons in its place.
- **`src/modules/docker/` (M2)** — agents are meant to "reuse one battle-tested implementation rather than reinventing the helpers per project." No agent prompt references it, and there is no tool; a containerized run hand-rolls Docker via Bash, the exact duplication M2 exists to prevent.

The architectural rule that closes this gap already exists for the config server: the **dual-callable surface rule** (R1-locked) — *every public API function is callable both via an MCP tool wrapper and via direct library import, same underlying function, never two implementations.* R7 generalises that rule from the Configuration API to the run-store resolution layer and the trace, safety, evaluator-core, and module libraries. Where a library exposes only an in-memory or stateful entry point (the trace emitter is a stateful class; some formatters take in-memory arrays), R7 adds a **single** thin disk-backed function that both the tool and any library caller share — preserving "never two implementations." It introduces no new *domain* logic; it makes already-shipped logic reachable from a markdown orchestrator.

### Five-question relevance filter

1. **Plugs into existing primitives?** Yes — it extends the existing framework MCP server and the R1-locked dual-callable pattern; it reaches around nothing.
2. **Composable by other agents/specs?** Yes — every downstream spec that assumes trace data exists (O2 recovery, O3 telemetry, T2 read CLIs, T3 budgets, E8) builds on the surface R7 exposes, without re-implementing it.
3. **Owns/accesses durable structured state?** Yes — it is the call path to zone-2 trace artifacts, the module-state store, and the deterministic evaluator plan.
4. **Fits existing ownership lanes?** Yes — same MCP server, same central-store and module-state write channels (F7/F8), same schema set; no new zone, no new ownership lane.
5. **Stackable / non-terminal?** Yes — it is pure infrastructure; its first invocation is the start of its usefulness, not the end.

Passes all five: this is infrastructure, and it is the keystone the v1.0 trust story depends on.

## Proposed change

Extend the **existing** framework MCP server (R1's `claudeagents-config` server) with four new tool groups, dispatched through the same table the config tools use. No second MCP server; no change to `install.sh`'s registration. Each tool wraps the same underlying function the library exposes (per the dual-callable rule), with the additions and exceptions called out below.

### Single server vs. a sibling (justification)

The new tools live in the existing server, not a sibling, because: one registration keeps `install.sh` and the restart-once contract unchanged; one dispatch table and one per-run log/trust context avoid duplicating R1's machinery; and the orchestrator already holds exactly one MCP connection. The server's name (`claudeagents-config`) is historical; its remit is "the framework's runtime API." The one risk a single server creates — a module that fails to load taking the whole server down — is eliminated by the lazy-load rule below.

### Tool groups

Argument and return shapes are the **existing** shapes except where noted; "Schema additions" lists the catalog growth. Run-scoped tools take an explicit run directory argument (the central-store run dir resolved per F7), mirroring how config tools take an explicit `projectRoot` — explicit arguments keep the tools deterministic and unit-testable.

- **Run context (`src/config-server/storage/`)** — split into a *pure* resolver and a *writing* workspace tool, because they have different call-times and the run lock must sit **between** them:
  - `resolveRunStore({ fromDir?, runId? })` → **pure** store-path resolution: mints a fresh run id via `generateRunId()` when `runId` is omitted, else takes an explicit one, and returns the library `ResolvedRunStore` struct — i.e. the tool is a **composition wrapper** (`generateRunId()` + the library `resolveRunStore`), **not** the bare library function, which *requires* `runId` and does not mint; same name, wider tool signature — (`storeRoot`, `repoKey`, `mainWorktreeRoot`, `repoStoreDir`, `runLockPath`, `runsRoot`, `runDir`) **plus the minted `runId`** — the tool's one addition, since `ResolvedRunStore` itself carries no `runId` field. **Runs no *user/build* command and writes nothing to zone 2** — pure path/string computation, aside from the one `git rev-parse --git-common-dir` read (whose parent is the main-worktree root). This is the keystone the lock and every run-scoped tool consume: it produces the `repoKey` that `acquireRunLock` needs and the `runDir` the trace/safety tools take, none of which the markdown orchestrator can compute itself (`resolveRunStore` / `generateRunId` / `computeRepoKey` are import-only). Called at **run start (before the lock)** and at every **`--recover` / `--cleanup` / `--list-recoverable`** (which need only the paths, never a new worktree).
  - `createRunWorkspace({ subject, runId, newWorktree? })` → resolves **and creates** the run's worktree by wrapping `resolveWorkspace`: it **writes** — cases 1b/1c run `git worktree add` / `git checkout` to create the branch and worktree on disk — and returns `{ worktreePath, branch, createdByGan, resolutionCase }`. `subject` is **required** (`resolveWorkspace` slugifies it into the branch name); `projectRoot` is **derived** internally from the resolved `mainWorktreeRoot`, not a caller argument. Because it writes zone-2, the orchestrator calls it **at run start only, *after* `acquireRunLock` succeeds** — the lock precedes **all** zone-2 writes (the clarifier's at step 7 *and* this worktree creation at step 8), per O2 §8 / SKILL.md, so this is one of the post-lock writes, not necessarily the first. **Recovery and cleanup never call it** — `--recover` re-attaches the *recorded* `workspace.worktreePath` from `progress.json` (O2 §5.4) and `--cleanup` removes it; only a fresh run creates a worktree. (An earlier single `resolveRunContext` tool conflated the two — it claimed to "write nothing" while wrapping the worktree-*creating* `resolveWorkspace`, would have created the worktree *before* the lock, and would have *re-created* it on recovery/cleanup. The split fixes all three.)
- **Trace (`src/trace/`)**
  - `emitTraceEvent({ runDir, event })` → appends one typed event and returns its `sequenceNumber`. **Stateless per call:** rather than wrapping the stateful `TraceEmitter` class, the tool calls a new shared function `appendTraceEvent(runDir, event)` that derives the next sequence from the run's trace index `totalEvents` (the O(1) fast path — the shipped `TraceIndex` carries `totalEvents`, not a high-water-sequence field), assigns that number, and writes the event file with **exclusive-create (`O_EXCL` / `wx`) on the `events/<seq>.json` path** — so a sequence collision *fails the write rather than silently overwriting it*; on `EEXIST` the function **re-derives the highest sequence from the authoritative `events/` directory — a one-shot scan, not the lagging index** — and retries (bounded). (Re-reading the index on retry could return the same stale highest sequence and re-collide, burning the retries without progress; the authoritative `events/` scan guarantees forward progress. The index is the O(1) fast path for the *no-collision* read only.) **If the bounded retry is exhausted it surfaces a structured warning (handled like the `agentAttempt`-emit failure below), never a silent drop.** This honours the established "the trace is the only counter" principle (the same source of truth recovery and the safety checks read), so no in-memory emitter state is required and there is one implementation behind both the tool and any library caller. The orchestrator is the intended **sole** trace writer for a run (as it is the sole writer of `progress.json` per SKILL.md), so collisions are not expected in normal operation — but the exclusive-create+retry is the defence-in-depth that prevents silent event loss if the markdown orchestrator ever fires a parallel tool call. (Plain temp-write+rename is unsafe here precisely because rename *overwrites*: two appends that read the same highest sequence would both target `events/N.json` and the second would clobber the first with no error.) **The per-run `index.json` is a *derived* artifact — a cache of counts/offsets over `events/`, not a second source of truth.** `events/` is authoritative; any reader or `--recover` reconciles the index from `events/` (via `reconstructRecoveryState`). The shared index write therefore stays a plain overwrite, and a lost index update under concurrent append is **self-healing** (it can undercount transiently but is rebuilt from the authoritative event files) — the "loses no event" guarantee rests on the exclusive-created event files, never on the index write. **The orchestrator's sole event-writer is `appendTraceEvent` (exclusive-create);** the shipped `TraceEmitter.persist` path writes via overwrite (`atomicWriteFile`), so the implementing PR must **not** route runtime emission through the emitter class — both must not write the same `events/` dir with conflicting collision semantics.
  - `runSprintSummary({ runDir })` and `formatHeartbeat({ role })` / `formatLlmCallSummary({ metrics })` → the stderr formatters (metadata only, never payload content). `formatHeartbeat`/`formatLlmCallSummary` wrap the existing in-memory formatters directly. `runSprintSummary` is a new shared disk-reading wrapper over `formatSprintSummaryFromEvents(events)` (the shipped function takes an in-memory array; the tool needs to scan the run dir) — a thin single-implementation function both the tool and library expose.
  - `reconstructRecoveryState({ runDir })` → wraps `reconstructRecoveryState(traceRoot)` — the per-role attempt accounting and generator fingerprint history rebuilt purely from `agentAttempt` events (the read substrate O2 and the safety tools share).
  - `buildTrustEventBody({ resolution })`, `buildValidationAbortBody({ stage, error })` (the shipped `buildValidationAbortBody(stage, error)` requires the `ValidationStage` discriminant — do not drop it) / `buildValidationAbortFromCode({ … })`, and `buildLoopDetectedBody({ … })` → the event-**body** builders, all shipped in `src/trace/integration.ts` (a trace-module surface, not safety). SKILL.md's run-trace integration points name them directly: the orchestrator "builds a `trustEvent` with the `buildTrustEventBody` builder", a `validationAbort` with `buildValidationAbortBody`, and the `safetyHalt` body with `buildLoopDetectedBody`, then emits the result via `emitTraceEvent`. The markdown orchestrator cannot import them, and hand-constructing the body forfeits the faithful `promptVariant`/`userChoice` mapping and the **verbatim** F2-error copy these builders guarantee. They wrap the shipped in-memory builders (one implementation behind tool and library). (The `createLoopDetectedError` / `createSprintBudgetError` / `createEditOscillationError` *error* builders are separate and live in `src/safety/` — see the Safety group.)
  - `aggregateRunSummary({ runDir })` → a **new** shared disk-reading wrapper over the shipped `aggregateSprintSummary(events)` that returns the **structured** `SprintSummaryAggregate` — the shipped fields are an `llmCall` count (`calls`), an `agentAttempt` count (`agents`), the three token sums, and the first-to-last `elapsedMs` span; there is **no** dollar/cost field and **no** `toolCall` count or per-call latency sum in the shipped aggregate, so do not imply one — the machine-readable counterpart to the `runSprintSummary` *string* formatter — **plus a `droppedEmits` count** read from the in-memory per-run emit-failure tally the config server holds (see "Trace emission is best-effort" below — in-memory so disk-full cannot defeat it). O3's `outcome.json` cost rollup maps onto these fields (`llmCallCount`←`calls`, the token sums, `wallClockMs`←`elapsedMs`) **plus a `toolCallCount`. Because the shipped aggregate does not count `toolCall` events, R7 adds one additive `toolCalls` counter** to `aggregateSprintSummary` (over the already-shipped `toolCall` event class) and the matching field to `SprintSummaryAggregate`, so `aggregateRunSummary` supplies O3's `toolCallCount` **day one** — no cross-spec seam, O3 consumes it without itself touching `src/trace/`. This is the lone bit of additive *counting* logic R7 adds; it stays single-implementation (tool and import both call the extended `aggregateSprintSummary`). **`droppedEmits > 0` is what lets O3 set `cost.complete: false` honestly:** a dropped cost-bearing emit leaves a *gapless, fully index-reconcilable* trace that is simply missing a logical event, so `reconcileTraceIndex` (which always rebuilds the index to equal the `events/` count) **cannot** detect the loss — the explicit counter must carry it, not the reconcile. Same single-implementation rule as `runSprintSummary`.
  - `reconcileTraceIndex({ runDir })` → wraps the shipped `reconcileIndex(traceRoot, runId)` and returns the rebuilt `TraceIndex` (including `totalEvents`) — the structured reconcile O3's index↔events consistency count and the concurrent-append AC both require (the index is a derived cache; this rebuilds it from the authoritative `events/`).
  - `reconstructRevisionState` is added to this trace tool group **by E8, not R7** (E8 § "Bounding thrash"). It filters `agentAttempt` events by an optional `contractRevision` field that **E8** adds to `run-trace-v1`, so R7 cannot ship it (R7 ships first) — E8 ships the field, the new pure helper (**not** an edit to the shipped whole-trace `reconstructRecoveryState`), and its tool wrapper together, extending the group R7 establishes here. R7's own deliverable surface does **not** include it (see Bite-size slices); the additive `contractRevision` field follows the schema-versioning ruling (roadmap § "Schema-versioning ruling"), the same way A1 added the `safetyHalt` class to `run-trace-v1`.
- **Safety (`src/safety/`)** — all pure, all consume reconstructed state:
  - `checkRoleCeiling`, `checkSprintBudget`, `detectEditOscillation` → the three halt decisions, with the same positional/object signatures the library exposes (the implementing PR pins the exact argument shapes in the api-tools catalog).
  - `createLoopDetectedError`, `createSprintBudgetError`, `createEditOscillationError` → the `LoopDetected` error builders (`src/safety/`). The matching `safetyHalt` *body* builder, `buildLoopDetectedBody`, is a `src/trace/` function and lives in the Trace group above.
- **Evaluator-core (`src/agents/evaluator-core/`)**
  - `buildEvaluatorPlan({ snapshot, sprintPlan, worktreeState })` → wraps `buildEvaluatorPlan(snapshot, sprintPlan, worktreeState)`. Returns a **plan**: data describing which commands to run and which surfaces fired — not execution (see "Relationship to F4").
- **Modules (`src/modules/`)** — **lazy-loaded** (see below):
  - `dockerReservePort`, `dockerReleasePort`, `dockerDiscoverPort`, `dockerCheckContainerHealth`, `dockerContainerName` → the `PortRegistry` / `PortDiscovery` / `ContainerHealth` / `ContainerNaming` helpers; registry state persists through the module-state store (F8). The implementing PR pins each tool's argument shape in the api-tools catalog. **`dockerReservePort` semantics (pinned, so M4 can write to it):** per the dual-callable + "no new *domain* logic" rules above, it is a **thin wrapper over the shipped `PortRegistry.register(worktreePath, port, containerName)`** — the **caller supplies the candidate port**, and "collision-free across concurrent runs" comes from `register` throwing `PortInUse` on a cross-worktree clash (`src/modules/docker/PortRegistry.ts:92`), **not** from R7 allocating a free port. There is no shipped free-port allocator (`PortRegistry` has no `reserve`/`allocate`; `PortValidator.isPortFree` is a separate helper), and building one (scan + `isPortFree` + `register`) would be new domain logic R7 does not add — a true allocator is a **future M2-extension spec**, not R7/M4. So M4's generator selects a candidate port and retries on `PortInUse` (see M4).
- **Run lock (`src/config-server/storage/run-lock.ts`)**
  - `acquireRunLock({ repoKey, runId })` / `releaseRunLock({ repoKey })` → the shipped portable `link(2)` run-lock O2's concurrent-run guard and `--recover` rely on. **`runId` is required on acquire, not optional:** the shipped `acquireRunLock` writes `runId` into the lock file, and `readRunLock` treats a lock *missing* a string `runId` as unreadable garbage that the next acquire **breaks and re-acquires** — so a `runId`-less lock would silently defeat the concurrent-run guard (a second `/gan` would break it and proceed). The tool therefore threads the `runId` that `resolveRunStore` minted (acquire needs both `repoKey`→`lockPath` and `runId`→lock contents; release only needs the path, hence release-by-key). **Stateless across the tool boundary (same treatment as `appendTraceEvent`):** the shipped `acquireRunLock` returns an in-memory `RunLockHandle` that `releaseRunLock(handle)` consumes — but an MCP tool pair cannot pass a JS handle between two separate calls, so R7 adds a thin shared **release-by-key** path (`releaseRunLock({ repoKey })` re-derives the lock path from `repoKey` exactly as acquire does), one implementation behind both the tool and the library, rather than threading the handle. (Both lock tools resolve the store root server-side via `resolveStoreRoot()` and then `resolveRunLockPath(storeRoot, repoKey)` — `repoKey` alone is insufficient to compute the path.) The orchestrator cannot issue the lock syscall directly; this is the lock the run loop acquires **and releases** (R7 wires both, per the lock-lifecycle note below; O2 §8's concurrent-run guard relies on it), **not** `flock`.

### Lazy module loading (must-fix — prevents a boot crash)

`src/modules/docker/index.ts` runs a prerequisite check (`docker --version`) **at import time** and throws `ModulePrerequisiteFailed` on a host without Docker. The config server wires its tools via top-of-file static imports; importing the docker tools the same way would execute that throw at server startup and take down **every** tool — `getResolvedConfig`, `validateAll`, all of it — on every Docker-less host (i.e. most hosts). Therefore the module tools MUST be loaded with a **dynamic `import()` inside the handler**, not a static top-level import. A host without Docker surfaces the manifest `errorHint` from the failed lazy import (error-text discipline) and the rest of the server is unaffected.

### Relationship to F4 (trust) and command execution

R7 widens the surface that *touches* commands, so its trust posture is explicit:

- **`buildEvaluatorPlan` returns data, never executes.** The plan lists command strings (audit/lint/test/build/doc-lint + `evaluator.additionalChecks`); execution stays the agent's job, under the PreToolUse confinement and the trust gate the orchestrator already passes. Per E1, the orchestrator runs `validateAll()` at run start, which surfaces `UntrustedOverlay` *before* any command-bearing path; the plan's commands therefore derive from already-validated config. The tool itself runs no command.
- **The docker exec tools run real processes**, so they honour the run's resolved trust posture: they are callable only within a run whose `validateAll()` trust check has passed; `--no-project-commands` suppresses project-sourced command behaviour for the run; and `GAN_TRUST=strict` fails closed in CI exactly as it does for the config path (F4/F6).
- R7 adds **no** new bypass of the trust ladder: data-returning tools cannot execute, and exec-capable tools inherit the existing gate.

### Emit-failure semantics

Trace emission is **best-effort and never aborts a run**: a failed `emitTraceEvent` (disk-full, EPERM) never throws to halt the run, and a missing `llmCall`/`toolCall`/milestone event degrades observability, not correctness. But it is **not silently swallowed** — every dropped emit increments a **structural per-run emit-failure signal: an in-memory `droppedEmits` tally the long-lived config server holds for the run** (the same process that serves `appendTraceEvent` and `aggregateRunSummary`), *in addition* to being logged. **It is in-memory by design, not an on-disk counter:** the headline failure is disk-full/EPERM, and an on-disk counter would share that exact failure domain — it could not record the very drop it exists to flag. An in-process tally survives a full disk (the config server is alive throughout the run — the same fact the run-lock's live holder pid relies on), and `aggregateRunSummary`, served by that same process, reads it directly at termination. This matters because the loss is otherwise **undetectable**: a dropped cost-bearing event leaves a gapless, fully index-reconcilable trace, so `reconcileTraceIndex` (which always rebuilds `index.json` to equal the `events/` count) reports "reconciles fine" — it catches only the self-healing index-lag case, never a real drop. O3's `cost.complete: false` therefore reads `droppedEmits`, **not** the reconcile (see O3 § "outcome.json"). The **one stronger exception** stays: a failed `agentAttempt` emit corrupts the attempt accounting the safety checks and recovery read, so the tool retries once and, on persistent failure, *also* returns a structured warning the orchestrator surfaces (the run continues, but the user is told the safety counters for that attempt are unreliable). **Residual (honest, and narrower than the disk-full an on-disk counter would miss):** the only loss `droppedEmits` cannot record is a config-server **crash/restart mid-run**, which zeroes the in-memory tally — but that is itself a catastrophic event after which O2's `--recover` re-reads the trace from disk, not a silent undercount of a still-running run. **Scope (the one dual-callable wrinkle):** because the tally is process-local, `aggregateRunSummary`'s `droppedEmits` is meaningful only when called **in the emitting server process** — which its sole consumer O3 does, in-process at termination. A separate-process library import of `aggregateRunSummary` (e.g. a CLI mirror) would see `droppedEmits: 0` since it never held the tally; the disk-derived sums are dual-callable as usual, only `droppedEmits` is process-scoped. An AC pins the structural-record behaviour and the `agentAttempt` warning.

### Confinement (unchanged)

Per E1/H1, MCP tool calls are not file-system reads and do not break the PreToolUse confinement; confined agents may call the new tools freely. The tools' own writes land in zones the hook already allows: trace events go to the F7 central-store run dir (allowed via the orchestrator-exported `GAN_RUN_DIR`), and registry state goes through the config server's module-state channel (F8). No new confinement grant is required.

### Performance

Emission is a single append: `appendTraceEvent` derives the next sequence from the index's `totalEvents` (O(1)), not a full event rescan, so per-call cost is one stat + one append + one index update — acceptable for the per-LLM-call/per-tool-call cadence. The implementing PR must avoid an O(n²) "reconstruct from all events on every emit" pattern.

### What R7 does not do

- It does not add a `gan run report` read CLI — that is T2 (v1.1). v1.0 users read trace files directly, per T1.
- It does not change any library's domain logic, thresholds, or data schemas.
- It does not decide *when* the orchestrator calls a tool — timing stays SKILL.md's responsibility (A1/T1/E8 prescribe it).
- It does not introduce a programmatic orchestrator; the orchestrator stays the `/gan` skill, now able to call the tools where SKILL.md names library helpers. D1 (status markers) flips the affected SKILL.md sections from aspirational to operative once R7 lands.

## Schema and surface additions

- **`schemas/api-tools-v1.json` grows** with one tool-input-schema entry per new tool, following the config server's existing precedent for tool additions (the implementing PR applies F3's schema-versioning rule as R1 already applies it to this catalog). The "no schema additions" claim of an earlier draft was wrong; this is the catalog growth.
- **New shared library functions** (single-implementation, exposed to both tool and library import): `appendTraceEvent(runDir, event)`, `runSprintSummary(runDir)`, and `aggregateRunSummary(runDir)` in `src/trace/` (each computes `traceRoot = join(runDir, 'trace')` before calling the library functions, which take `traceRoot` — the trace subtree under the run dir per T1's layout). These are thin disk-backed wrappers; the **only** new logic is the one additive `toolCalls` counter in `aggregateSprintSummary` (above, over the already-shipped `toolCall` event class), single-implementation. `resolveRunStore`, `createRunWorkspace`, and the body builders reuse existing functions unchanged.
- **No new data-shape *schema*.** Every tool serialises an existing shape: the run-store `ResolvedRunStore` + `ResolvedWorkspace` (run-context tool), `run-trace-v1` and `SprintSummaryAggregate` / `TraceIndex` (trace tools, including the `safetyHalt` body and `LoopDetected` error A1 already reserved), the evaluator plan type (E3), and `module-config-docker-v1` / module-state shapes (M2/F8). There are two scalar additions to `aggregateRunSummary`'s return, **both TS-return fields, neither a persisted JSON-schema artifact**: a `toolCalls` count (a new `SprintSummaryAggregate` field, counted over the already-shipped `toolCall` event class, supplying O3's `toolCallCount`), and a `droppedEmits` count backed by a small **in-memory per-run tally the config server holds** (not an on-disk artifact — see "Trace emission is best-effort"). `droppedEmits` specifically is an in-process emit-failure signal (so the schema-inventory convention lists neither addition) — produced here and consumed only by O3's `cost.complete` via the tool return. The trace event *classes* remain exactly `run-trace-v1`'s (no new event class lands in R7 — `independentReview` lands with E8). **One catalog-prose touch:** the implementing PR updates `schemas/api-tools-v1.json`'s top-level `description` (which today asserts "Every tool except `getApiVersion` takes at minimum `projectRoot: string`") to account for the new **run-scoped** tools that take `runDir`/`repoKey` instead of `projectRoot` — the per-tool catalog records are additive, but that description string must stay accurate.
- **SKILL.md F7-path reconciliation (residual stale-doc cleanup).** F7 relocated run *data* to the central store but left **several** `skills/gan/SKILL.md` references at the pre-F7 `.gan-state/runs/<run-id>/` *data* paths — the `progress.json` write ("Create the worktree" step), the `trace/` log ("Run-trace integration points"), the per-agent artefacts ("Spawn discipline"), **and the "Per-run state lives directly under …" lane note** (an earlier draft of this bullet listed only the first three and missed this one). R7's implementing PR corrects **all** `.gan-state/runs/<run-id>/` *data*-path occurrences to the central-store run dir (the `GAN_RUN_DIR` this spec's run-context tool resolves) — a sweep, not a fixed list — and leaves the project-local `worktree/` subtree alone (already correct). R7 owns this because it is the first post-F7 spec to make those exact SKILL.md sections operative; no other unimplemented spec named the cleanup.
- **Agent-prompt F7-path reconciliation (the symmetric half — load-bearing for confinement, not cosmetic).** The identical stale class lives in the six `agents/*.md` prompts: they instruct agents to write run *data* — the evaluator's evidence bundle (`agents/gan-evaluator.md:57,68`), the planner's `spec.md`, the proposer's contract drafts, per-run PID/artefact files — to the pre-F7 **project-local** `.gan-state/runs/<run-id>/…` literal path. (The **clarifier** prompt already phrases this abstractly — "under the run directory" — so it needs no sweep; the literal stale paths are in the proposer/reviewer/generator/evaluator/planner prompts.) Per F7 the H1 confinement hook derives its allowed zones from `GAN_WORKTREE` and `GAN_RUN_DIR` (the **central store**) and **denies everything else** (SKILL.md § "Confinement"), so an agent following its prompt would write to a path the hook **denies** — `gan-evaluator.md:57` even calls the project-local evidence-bundle path "designated", which F7 made false. R7's PR therefore sweeps the **data**-path references in `agents/*.md` to the central-store run dir the orchestrator exports as `GAN_RUN_DIR` into the spawn env (SKILL.md § "Spawn discipline"), leaving the project-local `…/worktree` references (i.e. `GAN_WORKTREE`) alone — the same data-vs-worktree split as the SKILL.md sweep above. F7's reconciliation list (F7 § "Specs reconciled") covers specs, **not** these prompt files, so the class is otherwise unowned; R7 claims it because it is the spec that makes the spawn/confinement path operative, and because E8's forced-verification evaluator write would otherwise be denied at runtime.
- **SKILL.md worktree-creation rewrite (fixes an observed regression — the direct payoff of exposing `resolveWorkspace`).** Step 8 ("Create the worktree") today names only the run-scoped *path* (`Use .gan-state/runs/<run-id>/worktree`) and leaves the create-vs-reuse decision to orchestrator interpretation. The tested decision engine that *should* make that call — `resolveWorkspace` (`src/config-server/storage/worktree-resolver.ts`, cases 1a/1b/1c) — has **no caller in `src/` and no tool/CLI surface**, so it never runs at runtime. Since F7 introduced reuse semantics (the 1a case, plus SKILL.md's "the user's own worktree when the run reuses a task-named worktree, or the run-scoped worktree the framework created otherwise"), runs started in the **main checkout** have begun executing *in place* instead of in a fresh worktree — the exact outcome `resolveWorkspace` (1b/1c) was written to prevent. R7's implementing PR rewrites step 8 to **call `createRunWorkspace`** (which wraps `resolveWorkspace`, after `acquireRunLock` has succeeded) and act on its returned `{worktreePath, createdByGan, resolutionCase}`: a run from the main checkout or a non-matching branch deterministically gets a fresh run-scoped worktree (1b/1c); only a dedicated non-main worktree is reused in place (1a). This is the dual-callable rule applied to the worktree decision — replacing prose that drifted with the shipped, tested logic — and is the most user-visible single payoff of this spec. **Lock lifecycle ownership (acquire *and* release land in R7, not just acquire).** `createRunWorkspace` writes zone-2 and must run *after* the run lock is held, but SKILL.md has no lock step today — so R7's step-8 rewrite wires the **full minimal lifecycle**: `acquireRunLock` at run start **right after `resolveRunStore` and before the *first* zone-2 write — which is the clarifier's `clarified-spec.md`/`raw-prompt.md` at step 7, *not* merely before `createRunWorkspace` at step 8** (per O2 §8, "the lock is acquired before any other zone-2 work"; placing it at step 8 would let a second concurrent `/gan` burn the whole interactive clarification phase before the `ConcurrentRunInProgress` refusal). `acquireRunLock` needs only `repoKey`+`runId`, both produced by the pure `resolveRunStore`, so it precedes every agent spawn and worktree op. **And** `releaseRunLock({ repoKey })` on **every** run-exit path, normal completion *and* abort/error. Release-on-exit **cannot** be deferred to O2: the shipped `acquireRunLock` records the *acquiring process's* pid, which in the MCP-tool context is the long-lived config server — so a lock left unreleased is held by a still-*live* pid, and the stale-break self-heal (which only fires for a *dead* holder) never clears it. Without R7 wiring release, run 1's lock would strand the repository against runs 2..N for the entire R7→E8→M4 window (three slots), every later run refused with `ConcurrentRunInProgress`. Stale-break itself comes for free with the shipped `acquireRunLock` (it probes holder liveness and breaks a dead-held lock), so the genuine *crashed-process* case is covered from R7. **O2 §8 (later in v1.0) owns the concurrent-run *guard contract* and the recovery/cleanup lock handling that build on this wiring** — AC 30's concurrent-run-refused message + `EXIT_INVARIANT_VIOLATION` mapping, the `--recover` / `--cleanup` lock semantics, and the stale-break operator notice — but the **basic acquire/release the loop needs to not wedge itself lands here, in R7**, not deferred to O2. (Once R7 wires `acquireRunLock`, a second concurrent `/gan` is already refused — the tool throws on a live holder — so O2 §8 specifies and *tests* that refusal contract rather than introducing it.)
- Any `gan` CLI mirror introduced for scripting (e.g. `gan run emit` for non-orchestrator callers) is a user-facing subcommand and lands in [`runtime-knobs.md`](runtime-knobs.md) in the implementing PR. The MCP tools themselves are an agent-facing surface (the tool catalog), not a user-facing runtime knob.

## Acceptance criteria

### Automated checks

- **Store resolver is pure and addressable.** `resolveRunStore` with no `runId` returns a fresh id matching `RUN_ID_PATTERN`, a `runDir` under `<storeRoot>/<repoKey>/runs/<runId>`, a `repoKey` byte-identical to the library `computeRepoKey` for the same worktree, and a `runLockPath` (informational — the `acquireRunLock` *tool* re-derives the lock path from `repoKey` server-side, it is not fed this field) — **creating no worktree and writing nothing**; called again with that explicit `runId` it resolves the **same** paths (recovery/cleanup/list addressability). Guards B1's pure-resolution half — the orchestrator cannot otherwise obtain the `runDir`/`repoKey` every later tool requires.
- **Workspace tool creates the worktree, after the lock.** `createRunWorkspace({ subject, runId })` returns `{worktreePath, branch, createdByGan, resolutionCase}` and, for cases 1b/1c, actually creates the branch + worktree (it wraps the writing `resolveWorkspace`); a test asserts it is **not** invoked on the `--recover` / `--cleanup` paths and is called only after `acquireRunLock`. Guards B1's create-half and the lock-before-any-zone-2-write ordering.
- **Run lock round-trips by key, and the written lock is readable.** `acquireRunLock({ repoKey, runId })` then `releaseRunLock({ repoKey })` (release-**by-key**, no JS handle threaded between the two tool calls) leaves the lock free, so an immediate re-acquire on the same `repoKey` succeeds; with the first lock still held by a *live* pid a second acquire is refused (`ConcurrentRunInProgress`). A companion check asserts the acquired lock is **readable** (`readRunLock` returns a record, not `undefined`) — i.e. the tool wrote a `runId` — because a `runId`-less lock would be treated as garbage and broken, silently defeating the guard. Guards the M1 release-by-key path — the stranding fix — at the tool level, independent of whether the markdown orchestrator obeys the SKILL.md release step (that half is the manual check below).
- **Structured cost + reconcile are derivable from the trace.** `aggregateRunSummary` returns a `SprintSummaryAggregate` whose sums equal those the library `aggregateSprintSummary` computes over the same events, and `reconcileTraceIndex` returns a `TraceIndex` whose `totalEvents` equals the authoritative `events/` file count — the structured sources O3's `outcome.json` rollup and index↔events count read (no markdown hand-summing).
- **Server boots without Docker.** With no `docker` binary on `PATH`, the MCP server starts and every config tool (`getResolvedConfig`, `validateAll`, …) responds; only the docker tools surface the manifest `errorHint` when invoked. (Guards the lazy-load rule.)
- **Trace is non-empty (tool-level, CI-runnable).** A harness that calls `emitTraceEvent` once per *simulated* agent attempt — **no LLM, no real `/gan` run** — produces a non-empty `trace/events/` with gapless sequence numbers and an index that resolves every event. This is the CI-testable form; CI has no LLM, so it cannot drive the markdown orchestrator. The end-to-end "a real orchestrated run actually emits a trace" assertion needs an LLM and is therefore **dogfood/manual-only** (tracked as a program risk in the roadmap, not a CI gate) — R7 proves the *tool* works and is *called* at the documented SKILL.md points, not that Claude obeys every emit instruction at runtime.
- **Concurrent append loses no event.** Two appends racing on the same run produce two distinct events (exclusive-create + retry), never a clobber; the event *count* equals the number of appends and the sequence is gapless — a gapless-but-lossy log (count < appends) fails this check. **And after the racing appends, `index.json` is verified *reconcilable* from `events/`: a reconcile pass makes `totalEvents` equal the event-file count** (the index is a derived cache, so a transient undercount is acceptable only if it rebuilds exactly from the authoritative events). Guards both the event-file race and the index lost-update.
- **Tool-vs-library parity.** For every new tool, a test asserts the tool handler and the direct library import call one underlying function (no second implementation) — including the new shared `appendTraceEvent` / `runSprintSummary` / `aggregateRunSummary` functions and the `buildTrustEventBody` / `buildValidationAbortBody` body builders.
- **Safety tools agree with the library** on a constructed attempt history (post-rejection guard and 3-cycle cases included).
- **Evaluator plan byte-identical** via tool vs library on the E3 pipeline fixtures.
- **Module state round-trips** and a duplicate reservation surfaces the existing `PortInUse` error.
- **Emit failure does not abort; it is structurally recorded; `agentAttempt` failure also warns.** Injected write failure on a non-`agentAttempt` event continues the run **and increments the server's in-memory `droppedEmits` tally** (surfaced by `aggregateRunSummary`, so O3 can set `cost.complete: false`) — not silently swallowed; the tally is asserted to increment **even when the run dir is unwritable** (the disk-full case the signal exists for), which an on-disk counter could not do. On an `agentAttempt` event it *also* returns the structured warning. A companion check pins G1: after a dropped emit, `reconcileTraceIndex` still reports the index reconciles to the `events/` count (the loss is invisible to the reconcile), so the only signal of the drop is `droppedEmits` — confirming the loss detector is the counter, never the reconcile.
- **No untrusted-command bypass.** `buildEvaluatorPlan` executes nothing (returns data only); a docker exec tool invoked under `GAN_TRUST=strict` without a passed trust check fails closed.
